# 完成定义

> **每一步验证都通过，不等于整个任务完成。** 每步验证只证明"这一步做对了"。完成定义是契约的一部分，在第④步写拆解方案时一起写明。来源：待争论问题 第 17 题。

## 每步验证会漏掉的三类

| 类型 | 例子 | 抓手 |
|---|---|---|
| **步骤之间的缝** | 两步各改了配置，单独都对，叠加后冲突 | 整体检查**先写、最后跑** |
| **代码以外的交付物** | 文档、迁移说明、changelog、给别人看的演示 | 项目默认写进常驻规则文件，任务特有的写进拆解方案 |
| **目标有没有达到** | 任务是"让页面变快"，每步都做完了，页面并没变快 | 目标写成可观察的结果；会话里验证不了的明写为已知缺口 |

三类在实践中都会遇到。

## 1. 步骤之间的缝：整体检查先写，最后跑

- 拆解方案的**第一步**写出整体验收的检查，此时它应该失败；最后一步让它通过。
- 写这个检查时，"整体做对是什么样"被迫说清楚；说不清楚，说明任务还没想明白，回到探索。
- 中间每一步都可以顺手跑一遍，缝隙不用等到最后才暴露。

这是把 [任务单元四条件](任务单元四条件.md) 的"可验证"从每一步扩展到整个任务。

## 2. 代码以外的交付物：分两层

- **项目默认的完成定义**（要不要更新文档、写 changelog、补迁移说明）写进常驻规则文件。它能通过 [上下文层](上下文层.md) 的准入测试：模型从代码里读不出来，每次任务都需要。Codex 官方也建议在 AGENTS.md 里写明"完成的含义和验证方式"，见 调研：规则文件官方建议。
- **只属于这个任务的交付物**（比如给某人看的演示）写进拆解方案的最后一步。

## 3. 目标有没有达到：写成可观察的结果

- "目标是 X"写成可观察的结果："首页加载从 3 秒降到 1 秒以内"，而不是"优化首页性能"。
- 会话里验证不了的（例如要等上线看真实数据），不假装验证过，在完成报告的"已知缺口"里写明：**由谁、何时、看什么**来确认。
- 这一类通常由你判断，模型自己宣布不算数，属于 [审查层](审查层.md) 的判断层。

## 分级

L0、L1 不用单独写整体验收，那唯一的一步就是整体验收。L2、L3 按上面三类写。见 [分级规则](分级规则.md)。
