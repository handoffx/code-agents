# 审查层

> **审查的是契约，不是 diff。** 机器负责证明，agent 的报告当作索引，人只做判断；审查深度与"发现 + 回退"能力成反比。

四层模型（见 Agent 与 Harness）里的最后一层：拿回来之后怎么确认。

## 审查的是契约

走完前面的流程后，手里已经有一份契约：[决策清单](决策清单.md) 上逐项表态过的决定，加上拆解方案里每一步写明的验证方式。审查就是**拿结果对照契约**，而不是盯着 diff 倒推 agent 的意图。

推论：**审查是否高效，在交出任务之前就已经决定了。**

## 三层审查

| 层 | 谁来做 | 检查什么 | 关键规则 |
|---|---|---|---|
| **证明层** | 机器 | 测试、类型、lint、构建 | 做的人不评判自己的活：测试由你写或由你审。独立审查 agent 默认不用，见下文 |
| **对账层** | agent 报告，你抽查 | 逐条核对契约：每个决策和验收标准是否落实、体现在 diff 的哪里、整体验收是否通过（见 [完成定义](完成定义.md)）、还有哪些已知缺口 | **报告是审查的索引，不能代替审查** |
| **判断层** | 只能是你 | 抽象是否合理、代码是否值得保留、品味 | 机器和清单都管不到的部分 |

对账层的风险最大：把 agent 对自己工作的描述当成审查本身（读书：Agentic Engineering 称之为"拿总结代替审查"）。报告只告诉你**该看哪里**。

## 理解到什么程度才能合并

（待争论问题 第 21 题。读书：Beyond Vibe Coding 主张"不合并你不理解的代码""作者解释不了就是红旗"）

| 层 | 理解到什么程度 | 什么时候必须做到 |
|---|---|---|
| **契约层** | 改了什么行为、接口和边界怎么变、为什么这样做 | **每次合并都必须**，说不清就不合并 |
| **实现层** | 每一行在做什么 | 只在证明层覆盖不到的地方：安全、并发、性能、数据完整性，以及 [分级规则](分级规则.md) 下限那几类改动 |

- 你既是作者又是审查者，书中的红旗落成一条规则：**合并前能用自己的话说清这次改动的契约**，与 [技能退化](技能退化.md)"说得出来"是同一个要求；说不清就细读，或让 agent"先讲给我听"
- 实现层不要求每次做到：证明层覆盖得到、发现快、回退易的细节交给测试；每行都要求读懂，审查会重新变成瓶颈
- 与书中立场的差别：书写于 AI 结对编程阶段，生成的是片段，逐行读懂成本不高；agent 一次改几十个文件时做不到，只能分层、按风险决定

## 验证证据：必须可核对

对账层核对的验证证据，按可信程度分三级（待争论问题 第 19 题，依据见 读书：Harness Engineering：证据必须来自本次运行中真实产生的观察）：

| 级别 | 来源 | 例子 | 怎么对待 |
|---|---|---|---|
| ① 机器产生 | CI、hook 或你自己跑的结果 | 停止前强制跑测试的 hook、CI 运行记录 | 最可信，证明层应该靠这一级 |
| ② agent 贴出原始结果 | 实际运行的命令 + 原始输出的关键几行 | `pytest tests/foo` → `12 passed` | 可以接受，你能自己重跑核对 |
| ③ agent 的叙述 | 只有结论 | "测试已通过""我验证过了" | **不接受**，等于没有证据 |

- **证据必须晚于最后一次修改**。常见情况是 agent 先跑测试通过，又改了几处，最后报告"测试已通过"：证据是真的，验证的却是旧代码（实际遇到过）
- 跑不了的验证（界面效果、需要真实环境的行为）：能截图或写出复现步骤就截图或写步骤；都做不到的不算"已验证"，写进完成报告的已知缺口（见 [完成定义](完成定义.md)）

## 审查深度：与"发现 + 回退"能力成反比

沿用 [验证能力决定粒度](验证能力决定粒度.md) 中验证能力的定义：

- **发现快、回退容易**（有特性开关的 UI 改动、内部工具）：证明层加抽查就够了，漏掉的代价很低
- **发现慢、回退难**（数据迁移、对外接口、鉴权）：逐行读，漏掉的错误很晚才暴露，而且撤不回来

把"每个 diff 都要认真审"这种做不到的要求，变成可以操作的分配原则：**把有限的注意力花在机器帮不上忙的地方。**

## 判断层只看契约层面的变化

模型训练从不惩罚可维护性的退化，所以证明层永远是绿的，代码却可能在几个月内固化（见 读书：Agentic Engineering 第 3 章）。但每个 PR 都审抽象质量也做不到。

沿用"先定接口，再写实现"的分工（见 [任务拆解](任务拆解.md)）：

- **判断层只看契约层面的变化**：新增或修改的接口、新引入的抽象、新增的依赖、模块边界的变化。这些都是决策，由你把关
- **接口内部的实现**属于已委托的部分，交给证明层和对账层
- "有没有新增或修改接口、有没有碰到范围以外的文件"**可以由机器检测**（比如用 hook 标记），用来引导判断层的注意力

## 反馈到上游

有些错误发现快、能回退，却会**反复引入**，比如 agent 每次都用错同一个 API。抽查兜不住这类问题。

审查层要有一个出口：**同一类问题第二次出现时，不再只是修掉它，而是反馈到上游**，变成规则、hook、测试或 skill（"每个错误都变成一条规则"，见 Agent 与 Harness、读书：Agentic Engineering 第 3 章）。

## 与分级的对应

| 级别 | 证明层 | 对账层 | 判断层 |
|---|---|---|---|
| L0 | ✓ | — | — |
| L1 | ✓ | agent 简短自述 | 仅当契约层面有变化 |
| L2 / L3 | ✓ | 逐项对照决策清单 | ✓ |

审查深度另外按"发现 + 回退"能力调整，与级别是两个独立的维度。见 [分级规则](分级规则.md)。

## 判断层会漏掉什么

判断层只看契约变化，会漏掉"接口没变、内部方向选错"（例如本该用状态机，写成了一堆 if）。来源有两种，处理不同（待争论问题 第 12 题）：

- **A. 单次方向选错，而且这个方向你在意**（更常见）：这是 [决策清单](决策清单.md) 漏了一项，问题在第③步，不在审查。决策清单要包括**实现方向的选择**（数据结构、状态管理方式、模块划分），**只要选错了以后很难改**；同类情况第二次出现时，在规则文件里写一条带原因的指引（见 [上下文层](上下文层.md)）。
- **B. 每次改动单独看都合理，累积起来变坏**：没有哪个决策是错的，逐个 diff 审查永远发现不了。把结构巡检挂到信号上：小需求的改动越来越大、修一个 bug 要动很多文件、agent 在同一模块里两次纠正还不对。出现信号时让 agent 对该模块做一次巡检，列出问题和重构候选，你来批。

## 独立审查 agent

待争论问题 第 13 题。实际用过，感觉不到明显效果，噪音多。

- **价值来自多样性，不来自能力**：全新的审查者有用，是因为它没看过做的人的推理过程（Claude Code 官方说法；书中 4 个工具对比 146 个 PR，93.4% 的问题只被其中一个发现）
- **噪音的原因**：审查 agent 手里没有契约，只能拿通用品味看 diff，不知道哪些是你定下的决策和故意的取舍
- **默认不用**。只在发现慢、回退难的改动上考虑（[分级规则](分级规则.md) 的下限那几类）。用的时候：
  1. **给它契约**：决策清单和 [完成定义](完成定义.md)，只查实现与契约是否一致，以及指定的几类风险（数据丢失、并发、鉴权）
  2. **每条问题必须带具体失败场景**："什么输入 → 什么错误结果"；写不出场景的不报，风格问题不报
  3. **记账**：用过几次后回头看，它找到的问题里有几个是你自己会漏掉的；没有就别用了
- 它的报告和对账层一样，只是索引
