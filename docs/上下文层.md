# 上下文层

> 规则文件（CLAUDE.md、AGENTS.md 之类）最常见的问题不是缺规则，而是**越积越多**：每踩一次坑加一条，文件越来越长，每条规则分到的注意力越来越少，重要的规则也被淹没。所以这一层的重点是**进出管理**。来源：待争论问题 第 16 题，官方依据见 调研：规则文件官方建议。

## 准入：什么能进常驻文件

每条规则都要通过两个问题，任何一个答"否"，就下放或删掉：

1. **模型从代码里读不出来吗？** 架构、目录结构、依赖列表不写，模型会自己读。
2. **每次任务都需要吗？** 只在某类任务或某部分代码里用到的，按需加载。

能通过的通常是：验证命令、项目默认的完成定义（见 [完成定义](完成定义.md)）、代码里会误导人的地方（到处在用但新代码不能照抄的旧写法）、仓库里没有记录的决策、已经纠正过两次的错误。

**加规则的时机**：同类问题第二次出现时（与 [审查层](审查层.md) 的"反馈到上游"一致），只在真实失败之后。

## 写在哪：能往下放就往下放

| 优先级 | 去处 | 适合放什么 |
|---|---|---|
| 1 | 机器强制（测试、lint、hook、deny 规则） | **零例外**的规则。有例外的规则即使能检查，也留给模型判断 |
| 2 | 按需加载（skill、按路径生效的规则、子目录规则文件） | 只在某类任务或某部分代码里需要的知识和流程 |
| 3 | 常驻规则文件 | 每次任务都要用、又不是零例外的规则 |

机器强制的规则也要少，每一条都会偶尔误伤，也都要有人维护。只是偏好的 hook 应该删掉，交还给模型判断。

**信号**：一条规则加了强调（IMPORTANT、大写）模型还是漏掉，原因只有两种：文件太长、这条被淹没了，或者它本该是机器强制的。继续加强语气没用，反而会让模型过度套用。

## 规则还是判断：三个去处

"规则还是判断"不是二选一，判断的人可以是模型，也可以是你（待争论问题 第 4 题）：

| 谁来定 | 机制 | 适合 |
|---|---|---|
| harness 强制 | hook、deny 规则、lint | 零例外 |
| 模型判断 | 规则文件里的指引，写明原因 | 有例外，选错代价低 |
| **你判断** | [决策清单](决策清单.md)、[分级规则](分级规则.md) 的下限 | 有例外，选错代价高 |

按"有没有例外"和"选错的代价"交叉：

| | 选错代价低 | 选错代价高 |
|---|---|---|
| **零例外** | 格式化、lint，成本低就做 | hook、deny 规则 |
| **有例外** | 指引，或什么都不写，交给模型默认 | **不写成规则，交给你判断** |

右下角最容易处理错：hook 硬拦会误伤例外，写进规则文件又等于让模型自己决定何时例外。例如"不要删数据"，按分级下限，删除数据至少 L2，进决策清单由你拍板。

**随时间怎么移动**（与 [两个旋钮](两个旋钮.md) 的决策委托旋钮一致）：

- 信任增加时，事情从"你判断"移到"指引"，再移到"什么都不写"。决策清单里总是"交给你判断"的同类决策下次不再列，就是这个方向。
- hook 不随信任移动。它存在的原因不是模型判断差，而是"几乎每次都对"不够。换更强的模型时，指引和决策清单都该清理，hook 只清理那些其实只是偏好的。

## 怎么写

- 格式：**什么场景 → 怎么做 → 为什么**。写明原因，模型遇到边界情况才能自己判断。
- **写明做什么，不规定怎么做**（读书：Agentic Engineering）：每规定一个实现细节，就拿走一份判断空间。写成"目标、约束、原因"，例如"这个接口要兼容旧客户端，因为有一批设备不能升级"，而不是一串步骤。
- 具体，不要泛泛。写"API handler 放在某目录"，而不是"保持文件有条理"。
- 模型本来就会做对的事不写。
- **来源写进添加这条规则的提交说明**，不写进规则文件。文件更短，删的时候查 git 就知道当初为什么加。
- 规则之间互相矛盾时，模型可能随便选一条执行，所以改规则要顺手查冲突。

## 何时删

**长度只是报警线，不是预算。** 用工具官方给的阈值（例如 Claude Code 单文件建议不超过 200 行；Codex 合计默认 32 KiB，超出就截断，中文按字节计会更快到）。一报警就做一次分拣。主要判据仍是上面的准入测试。

删规则没有事件触发，所以要**挂到已有的事件上**：

| 事件 | 顺手做的事 |
|---|---|
| 长度报警 | 分拣一次 |
| 某条规则改成了机器强制 | 在同一个提交里删掉文字版 |
| 换了更新的模型 | 清理一次：很多规则是给旧模型打的补丁 |
| 对应的代码或场景不存在了 | 删掉 |

**清理交给 agent 初筛，你来批**（与 [决策清单](决策清单.md) 同一模式）。让 agent 对照代码列出候选：引用的路径或命令已经不存在、已被 lint 或测试覆盖、互相重复或矛盾、为旧模型写的、看不出为什么存在。你逐条回复"删 / 下放 / 保留"。

**大胆删。** 删规则可回退（git 里还在），也能发现（模型再犯同样的错，你马上会看到）。按 [验证能力决定粒度](验证能力决定粒度.md) 里"验证能力 = 发现 + 回退 + 证明"，这类改动可以乐观处理：拿不准的先删，犯错了再加回来，加回来时在提交说明里写清来源。

**已经很长的文件**：做一次分拣，每条规则归入"下放为机器强制 / 下放为按需加载 / 保留 / 删除 / 不知道为什么存在"，最后一类按"大胆删"处理。
