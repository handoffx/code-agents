# 分级规则

> 按"有没有我在意、但还没定下来的决策"给任务分级，按级别截取流程。拆解的成本因此和不确定性成正比，只花在真正有返工风险的地方。

## 为什么不按任务大小分

改动行数和工作量都不是好标准：
- 一行代码的改动可能牵涉重要决策，比如改默认超时时间
- 一千行的机械搬迁可能一个需要你拍板的决策都没有

框架是围绕决策和验证建立的（见 [两个旋钮](两个旋钮.md)），分级也用同样的标准。

## 前置问题：这件事值得做吗？

只在一种情况下必须问：**任务是由 agent 提出的，而不是你提出的。**

- 你自己提出的任务，提出时就已经回答过"值不值得做"
- agent 提出的任务（调研后的建议、"顺便发现可以改进"的地方），没有人回答过
- 这是任务**之上**的决策，不会出现在 [决策清单](决策清单.md) 里，因为清单只覆盖任务内部的决策
- 不对每个任务都问，否则很快沦为走过场
- 回答"值得做"时，对价值不高的任务顺便定一个**预算**（如"最多值一小时"）。到了预算还没做完，整个放弃，不被沉没成本牵着走（见 [任务拆解](任务拆解.md)"做到八成"）

来源：读书：Agentic Engineering 中作者的竞品 PR 险情，所有检查都是绿的，但功能本身不该存在。见 待争论问题 第 10 题。

## 分级问题

动手前用几秒钟问自己：

> **这个任务里，有没有我在意、但还没定下来的决策？**

| 回答 | 级别 | 流程 |
|---|---|---|
| 没有 | **L0 直接做** | 一句话的指令，加上验证命令 |
| 有，而且知道是哪几个 | **L1 自带决策** | 在指令里直接写明决策，模型照做并验证 |
| 有，但列不全 | **L2 决策清单** | 模型列 [决策清单](决策清单.md) → 逐项表态 → 拆解方案 → 小步执行 |
| 不知道会有哪些决策 | **L3 完整流程** | 探索（可写原型）→ 决策清单 → 拆解方案 → 小步执行 |

例子：
- **L0**：修拼写错误、按已有模式加一个字段、修一个原因很清楚的失败测试
- **L1**："加分页，用游标而不是偏移，每页默认 50 条"
- **L2**：给现有模块加退款功能，大致知道涉及部分退款、幂等，但不确定是否还有别的
- **L3**：接入没用过的支付服务商，或在陌生代码库里做改动

**L1 就是由你自己填好的决策清单。** 四个级别不是四套流程，而是同一套流程按需截取：级别越低，跳过的前置步骤越多。

### 不需要单独的"验证"维度

没有现成的验证手段时，"怎么验证"本身就是一个需要你拍板的决策，会自然把任务推到 L1 或更高。

## 规则一：从低级别起步，看到信号就升级

分级不可能每次都准，所以目标不是一开始就分对，而是让分错也便宜：
- 执行中暴露出新的决策（[决策清单](决策清单.md) 的补充规则）→ 升一级
- 触发两次纠正规则（见 [任务拆解](任务拆解.md)）→ 级别判断低了，回到更高级别重新开始
- L0、L1 任务没拆解，做到八成卡住 → 级别判断低了

有补充规则兜底，低估只浪费一小段会话；高估则每个任务都要走一遍繁重的流程。所以默认乐观起步。

## 规则二：不可逆的改动有级别下限

选错代价高、难以回退的改动，不管看起来多简单，**至少按 L2 处理**：
- 数据库迁移、删除数据
- 对外公开的接口和数据格式
- 鉴权、权限、密钥相关的改动
- 依赖的升级或替换

理由：这类改动的错误往往上线后才暴露，补充规则兜住时已经晚了。

这条下限不是额外的补丁，而是可以从 [验证能力决定粒度](验证能力决定粒度.md) 推出来：这些改动的**发现**慢、**回退**难，验证能力天然不足。反过来，如果为某类改动补上了发现和回退手段（比如可回滚的迁移、带特性开关的接口），它的下限也可以相应放宽。

## 级别与文档长度是两回事

- **级别**（按未定决策分）决定走流程的**哪几步**
- **规模**决定规格和清单写**多长**

读书：Agentic Engineering 按规模把规格分为三种形态：一次性（100–300 字）、功能（500–1000 字，约 800 字为上限）、项目（2000–5000 字）。经验法则：**规格比预期的 diff 还长，就是写过头了。**

书中"30 分钟以内、少于 3 个文件、不碰公共接口就不做冲刺契约"的门槛里，"不碰公共接口"其实是风险判断，对应本笔记的不可逆下限。见 待争论问题 第 11 题。

## 对"拆解的成本谁来付"的回答

成本和不确定性成正比。大部分日常任务落在 L0、L1，几乎没有额外成本；完整流程只留给陌生或高风险的任务，而这些恰恰是不拆解最容易大面积返工的。
