# 技能退化

> 要紧的退化不是"不会写代码"，而是**不了解自己的系统**。框架里所有需要你判断的环节（[决策清单](决策清单.md)、判断层）都依赖它；它一旦退化，这些环节会悄悄失效，流程表面照常。来源：待争论问题 第 6 题。

## 哪些退化要紧

| 技能 | 要紧吗 | 原因 |
|---|---|---|
| 写代码的熟练度 | 不要紧 | 框架不依赖它。实际已经退化 |
| 在代码层面挑细节错误 | 不算退化问题 | 取决于是否完整读了代码，是 [审查层](审查层.md) 审查深度的选择；要防的是该细读的地方没细读 |
| **对自己系统的理解** | **最要紧** | 决策清单上每项"选错的代价"都靠它判断 |

实际经验：系统理解的退化通常是在**某个决策选错之后**才发现，已经晚了。

## 最早的信号：批了但说不清为什么

这种情况经常遇到。原因有四种，以前都变成了"同意"，所以分辨不出来：

| 原因 | 处理 |
|---|---|
| ① 其实不在意 | 回"交给你判断"，下次不再列 |
| ② 信息不够：选项和代价没落到你的系统上 | 回"补充信息" |
| ③ 不了解这一块：系统理解退化 | 回"先讲给我听" |
| ④ 清单太长，批累了 | 清单要短，① 类及时清走 |

对策是**给"同意"设门槛**，回复选项见 [决策清单](决策清单.md)：说不出一句理由就不能回"同意"。这样 ③ 从"决策选错后才发现"变成"表态时就发现"，每次"先讲给我听"都补上一块系统理解，对抗退化不需要另花时间。

另外，每项决策附上**它依赖的系统事实**（如"因为 X 模块同时被 Y 和 Z 调用"）。核对事实比做判断容易：事实对了，判断有依据；事实错了，当场就能发现。

## 挂在已有环节上的对策

1. **说得出来**：L2 及以上的任务完成后，能用自己的话讲清改了什么、为什么这样改；讲不清就回去细读
2. **测试偏向自己写**：改变行为型任务的失败测试由你写或由你审，偏向自己写，保住"想清楚什么是对的"的能力
3. **卡住时偶尔自己来**：按两次纠正规则丢掉会话后，有时自己调试，不要每次都重开 agent
4. **"交给你判断"时自检**：如果它选错了，我能看出来吗？能，是信任；不能，是退化。决策委托旋钮放开有这两种原因，从外面看完全一样（见 [两个旋钮](两个旋钮.md)）
