# 方法论总览

> 拿到一个任务，该怎么交给 code agent，又怎么确认它做对了。本篇只整合已达成共识的结论，细节见各篇链接。

## 五条核心命题

1. **任务粒度由验证能力决定，不由模型能力决定。** 验证能力 = 发现 + 回退 + 证明。见 [验证能力决定粒度](验证能力决定粒度.md)
2. **拆解的单位是决策，不是代码行数。** 见 [任务单元四条件](任务单元四条件.md)
3. **两个旋钮：验证粒度和决策委托。** 前者受你的验证能力限制，后者受你对模型的信任限制；模型进步拧动的是后者。见 [两个旋钮](两个旋钮.md)
4. **成本与不确定性成正比。** 按"有没有我在意、但还没定的决策"分级，按级别截取流程。见 [分级规则](分级规则.md)
5. **审查的是契约，不是 diff。** 审查深度与发现 + 回退能力成反比。见 [审查层](审查层.md)

公开仓库 [handoffx/code-agents](https://github.com/handoffx/code-agents) 的 README 收录了下面这份概述（2026-10-28），写给没读过我们讨论的人：

> 这套方法与具体工具和项目无关，插件只是它在 Claude Code 上的一种落地。五条核心命题：
>
> 1. **任务粒度由你的验证能力决定，而不是模型能力。** 验证能力包括三部分：发现错误、回退改动、证明正确。你验证不了的步骤，就不该一次交出去
> 2. **拆解的单位是决策，不是代码行数。** 你在意、但还没定的决策，在执行前就要摆出来让你定；执行中冒出新的决策，agent 要停下来问，不能自己做掉
> 3. **执行上下文和验收节点分开。** 给 agent 完整的目标和背景，同时让它小步交付、每步给出能核对的证据：贴出实际运行的命令和输出，只说"测试已通过"不算证据
> 4. **成本和不确定性成正比。** 按"有没有未定的决策"分级，简单任务直接做，复杂任务才走决策清单和完整拆解；数据迁移、改接口、鉴权、依赖升级这类改动出了错发现慢、回退难，至少走决策清单
> 5. **审查的是契约，不是 diff。** 机器负责证明，agent 的报告只当索引，人只判断契约层面的变化：新接口、新抽象、新依赖、模块边界。审查深度与发现和回退能力成反比

## 流程

```
⓪ 值得做吗？（仅限 agent 提出的任务）
        ↓
① 分级：有没有我在意、但还没定的决策？ ──→ 不可逆改动至少 L2
        ↓
② 探索（L3）：可写原型，交付物是结论和决策清单
        ↓
③ 决策清单（L2+）：逐项表态；L1 由你在指令里直接写明
        ↓
④ 拆解方案：每一步写明怎么验证；首尾是整体验收
        ↓
⑤ 小步执行：大上下文，小步验收
   ├─ 发现新决策 → 停下来加进清单，升一级
   └─ 纠正两次还不对 → 丢掉会话，回到 ①
        ↓
⑥ 审查：证明层 → 对账层 → 判断层
        ↓
⑦ 反馈到上游：同类问题第二次出现 → 变成规则 / hook / 测试 / skill
```

### ⓪ 值得做吗

只在**任务由 agent 提出**时必须问：调研后的建议、"顺便发现可以改进"的地方。你自己提出的任务，提出时已经回答过。价值不高的任务顺便定一个预算，到了还没做完就整个放弃。见 [分级规则](分级规则.md)。

### ① 分级

| 级别 | 判断 | 走哪几步 |
|---|---|---|
| L0 | 没有未定决策 | ④ 简化为一句话指令 + 验证命令 → ⑤ → ⑥ |
| L1 | 有，知道是哪几个 | 在指令里写明决策 → ④ → ⑤ → ⑥ |
| L2 | 有，但列不全 | ③ → ④ → ⑤ → ⑥ |
| L3 | 不知道会有哪些决策 | ② → ③ → ④ → ⑤ → ⑥ |

- **乐观起步，看到信号就升级**
- **下限**：数据迁移、删除数据、对外接口与数据格式、鉴权与密钥、依赖升级，至少 L2。原因是这些改动发现慢、回退难；补上发现和回退手段后，下限可以放宽
- 级别决定走哪几步，规模决定文档写多长；规格比预期的 diff 还长，就是写过头了

### ② 探索（L3）

产出是知识，不是代码。允许写原型，但原型只为决策清单提供证据，默认丢掉。见 [任务拆解](任务拆解.md)。

### ③ 决策清单（L2 及以上）

- 只列**选错了会影响你**的决策；每项写明可选方案、模型的倾向、选错的代价
- 逐项回复：同意 / 选另一个 / 交给你判断 / 补充信息 / 先讲给我听。**回"同意"要能说出一句理由**，说不出就选后三种之一（见 [技能退化](技能退化.md)）
- 同类决策总是"交给你判断"，下次就不再列，这就是在放开决策委托旋钮。回之前自检：如果它选错了，我能看出来吗？
- 只覆盖任务内部的决策，"值得做吗"由 ⓪ 处理

见 [决策清单](决策清单.md)。

### ④ 拆解方案

- 每一步都写明怎么验证；写不出验证方式，说明这一步还没准备好
- 按验证方式分三类：**探索型**（能否据此做决策）、**保持行为型**（现有测试全过，且断言一行不改，机械性改动单独列出）、**改变行为型**（先有会失败的测试，测试由你写或由你审）
- 顺序：整体验收的检查放第一步；不确定性高的先做；每一步结束时系统都能跑（纵向切片）；先定接口，再写实现
- **整体验收**（L2 及以上）：每步验证都通过，不等于整个任务完成。第一步写出整体验收的检查（此时失败），最后一步让它通过，并按项目的完成定义交付文档等非代码产出；目标写成可观察的结果，会话里验证不了的写进已知缺口

见 [任务拆解](任务拆解.md)、[完成定义](完成定义.md)。

### ⑤ 小步执行

- **大上下文，小步验收**：给全目标和全背景，每个验证节点停下来交证据
- **新决策停下来问**：执行中发现清单外、选错了会影响你的决策，加进清单等你表态，并升一级
- **并行**：agent 停下来等你时先给复位卡；后台任务不限数量，同一时间只有一个任务处在需要你判断的阶段；做完手上的判断再切换。见 [并行多 agent](并行多%20agent.md)
- **两次纠正规则**：纠正两次还不对，丢掉会话，把暴露出的决策显式做掉，开一个干净的任务。上下文只分配不释放，继续纠正只会更乱。丢掉前把走不通的方案记进任务文件
- **做到八成**：剩下的只是执行就补完；有没暴露的决策或方向错了，丢掉代码、保留任务文件、回到拆解；补完的代价超过价值就整个放弃。见 [任务拆解](任务拆解.md)
- **任务文件**（L2 及以上）：决策（只追加）、已排除的方案（只追加）、拆解与进度、复位卡写进仓库里一个不提交的文件；新会话从它接着做。见 [任务文件](任务文件.md)

### ⑥ 审查

| 层 | 谁 | 做什么 |
|---|---|---|
| 证明层 | 机器 | 测试、类型、lint、构建；做的人不评判自己的活 |
| 对账层 | agent 报告，你抽查 | 逐条对照契约；**报告是索引，不能代替审查**；验证证据要可核对：命令 + 输出，晚于最后一次修改 |
| 判断层 | 你 | 只看契约层面的变化：新接口、新抽象、新依赖、模块边界 |

审查深度与发现 + 回退能力成反比：发现快、回退易的改动靠抽查，发现慢、回退难的改动逐行读。见 [审查层](审查层.md)。

### ⑦ 反馈到上游

同一类问题第二次出现时，不只是修掉，而是变成规则、hook、测试或 skill。去处按"零例外的机器强制 → 按需加载 → 常驻规则文件"的顺序选；常驻文件只收模型从代码里读不出来、每次任务都需要的规则。删除挂到已有事件上（长度报警、改成机器强制、换模型、代码不存在），由 agent 初筛、你来批。见 [上下文层](上下文层.md)、[审查层](审查层.md)。

## 统一提示词模板（L2 / L3）

> 目标是 X（写成可观察的结果），背景是 Y。先不要动手。
>
> 1. （L3）先探索：弄清 Z。可以写原型，但原型只用来给后面的决策提供证据，用完丢掉。
> 2. 列出完成目标需要做的决策，只列选错了会影响我的；包括实现方向的选择（数据结构、状态管理方式、模块划分），只要选错了以后很难改。每项给出可选方案、你的倾向和理由、选错的代价、这项判断依赖的系统事实。
> 3. 等我逐项表态后，给出拆解方案，每一步写明怎么验证。第一步写出整体验收的检查，最后一步让它通过，并按项目的完成定义交付文档等非代码产出。
> 4. 我确认后按步骤执行，每完成一步停下来给出验证证据：贴出实际运行的命令和关键输出，必须在最后一次修改之后运行；只有结论的描述不算证据。
> 5. 执行中发现清单外、选错了会影响我的新决策，停下来问我，不要自己做掉。
> 6. 完成后逐条说明每个决策和每步验证是否落实、体现在 diff 的哪里、还有哪些已知缺口；说明整体验收是否通过；目标层面会话里验证不了的，写明由谁、何时、看什么来确认。
>
> 凡是停下来等我（等表态、等审、卡住），先给一张复位卡：任务目标、现在在拆解方案第几步、为什么停、需要我做什么、我之前定过的相关决策。同时更新任务文件：决策和已排除的方案只追加，进度可以覆盖，复位卡放在文件开头。新会话先读任务文件。

## 整合时发现的问题

整合过程中发现以下不一致和缺口，记为 待争论问题 第 14–17 题。第 1、2 条已于 2026-10-28 修正，第 3、4 条已结论：

1. **"决策单一"与决策清单的关系不清**：[任务单元四条件](任务单元四条件.md) 要求每个任务"你在意的决策最多一个"；但走完决策清单后，执行步骤里应该**没有**未定的、你在意的决策了，新出现的走补充规则。**已改**为"无未定决策"。
2. **[两个旋钮](两个旋钮.md) 里的提示词已过时**：那里写的是"先提出拆解方案，等我确认后再动手"，早于决策清单。**已改**为引用本篇的统一模板。
3. **上下文层没有自己的结论**：⑦ 产出的规则最终落在上下文层，但这一层目前只有外部资料（Agent 与 Harness、读书：Agentic Engineering），还没有讨论过"规则写在哪、怎么写、何时删"。**已结论**，见 [上下文层](上下文层.md)
4. **整体的完成定义缺位**：契约由"决策 + 每步验证"组成，但没有覆盖整个任务的完成定义（书中称为 definition of done，比如文档更新、演示录屏）。每步验证都通过，是否就等于整个任务完成？**已结论**：不等于，见 [完成定义](完成定义.md)
