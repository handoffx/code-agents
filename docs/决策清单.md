# 决策清单

> 让模型拆解任务时，不要只让它给出拆解方案，而是先让它列出**需要你拍板的决策清单**。审批从"判断计划合不合理"变成"逐个对决策点头或摇头"。

## 为什么

- "让模型拆、由你来批"（见 [两个旋钮](两个旋钮.md)）的风险是**审批走过场**：模型给出的方案往往看起来都合理，人很容易直接批准
- 防止走过场靠的不是"审得更认真"，而是**改变审批的形式**
- 一个整体的计划只能整体批准或否决；拆成一个个决策后，每项都要你明确表态，很难敷衍
- 正好对应**决策委托旋钮**：清单就是这个旋钮的具体刻度

## 范围

清单只覆盖任务**内部**的决策。"这件事值得做吗"在任务之上，由 [分级规则](分级规则.md) 的前置问题处理。

实现细节不列，但**实现方向的选择**要列：数据结构、状态管理方式、模块划分，只要选错了以后很难改。方向选错是"接口没变、内部选错"最常见的来源，见 [审查层](审查层.md)（待争论问题 第 12 题）。

## 形式

每个决策项包括：

| 字段 | 说明 |
|---|---|
| 决策 | 要决定什么 |
| 可选方案 | 至少两个 |
| 模型的倾向 | 选哪个、为什么 |
| 影响 | 选错了的代价，是否容易回退 |
| 依赖的系统事实 | 这项判断依据的事实，如"X 模块同时被 Y 和 Z 调用"。核对事实比做判断容易 |

审批时逐项回复：

| 回复 | 什么时候用 |
|---|---|
| 同意 | **能说出一句理由**；说不出就不能回同意 |
| 选另一个 | 你有不同选择 |
| 交给你判断 | 其实不在意 |
| 补充信息 | 选项和代价太抽象，要求落到具体代码：涉及哪些模块、以后哪里会变难改 |
| 先讲给我听 | 你不了解这一块，让模型先讲清现在怎么工作，再决定 |

"同意"的门槛和后两个选项来自 [技能退化](技能退化.md)（待争论问题 第 6 题）："批了但说不清为什么"是系统理解退化最早的信号。

"交给你判断"就是在拧决策委托旋钮：同类决策如果你总是这么回，下次就不必再列进清单。回之前自检：如果它选错了，我能看出来吗？不能，就不是信任，而是退化。

## 补充规则：执行中暴露的决策

有些决策只有在验证时才会暴露，比如测试跑起来以后，才发现某个边界情况需要你来定怎么处理。这类决策没法提前列进清单。

> **规则：执行或验证时发现新的决策，模型要停下来把它加进清单、等你表态，而不是自己顺手做掉。**

- 这就是两个旋钮的耦合点：验证节点会产出新的决策（见 [两个旋钮](两个旋钮.md)）
- 和 [任务拆解](任务拆解.md) 中的"两次纠正规则"吻合：反复纠正往往说明有一个没暴露的决策。区别在于，这条规则让模型**主动**暴露决策，而不是等你纠正两次才发现
- 判断标准和列清单时一样：只有**选错了会影响你**的才算，实现细节照常自行处理

## 提示词模板（草拟，可调整）

> 目标是 X，背景是 Y。先不要动手。
>
> 1. 列出完成这个目标需要做的决策，只列那些**选错了会影响我**的，实现细节不要列，但选错了以后很难改的实现方向要列。每项给出可选方案、你的倾向和理由、选错的代价、这项判断依赖的系统事实。
> 2. 等我对每项表态后，再给出拆解方案，并写明每一步怎么验证。
> 3. 执行中如果发现清单外、选错了会影响我的新决策，停下来加进清单问我，不要自己做掉。

## 证据来源：探索原型

决策项里的"可选方案"和"倾向"可以有原型作为证据。探索阶段允许写原型，但原型只服务于清单，默认丢掉，见 [任务拆解](任务拆解.md) 的探索型任务。

## 什么时候用

按 [分级规则](分级规则.md)：L2、L3 由模型列清单；L1 相当于你自己在指令里填好了清单；L0 不需要清单。

## 与拆解方案的关系

先定决策，再拆步骤。决策定下来以后，拆解方案基本就由决策决定了，审起来也快得多。
