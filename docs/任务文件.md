# 任务文件

> **会话会丢，决策不能跟着丢。** L2 及以上的任务，把决策、已排除的方案、拆解与进度写进一个任务文件。丢掉会话重开时，新会话从这个文件接着做，而不是靠你凭记忆重新交代。来源：待争论问题 第 20 题，依据见 读书：Harness Engineering 第 2 章（模型只能对当前上下文里的状态做决策，任务不能依赖某次会话一直存在）。

## 为什么需要

- 按 [任务拆解](任务拆解.md) 的两次纠正规则丢掉会话时，聊天里的决策清单表态、拆解方案、做到第几步，会全部跟着丢掉
- 失败的会话也有价值：它说明了哪条路走不通。不留下来，新会话很可能再走一遍同样的弯路
- 并行时，复位卡（见 [并行多 agent](并行多%20agent.md)）如果每次都从聊天记录临时拼，还是要靠 agent 和你的记忆

## 适用范围

只用于 L2 及以上（见 [分级规则](分级规则.md)）。L0、L1 一个会话就能做完，不值得多一个文件。

## 内容与写入方式

| 部分 | 内容 | 写入方式 |
|---|---|---|
| **复位卡** | 放在文件开头：目标、在第几步、为什么停、需要你做什么、相关决策 | 每次停下来时重写 |
| **决策** | [决策清单](决策清单.md) 每一项和你的表态，包括执行中新冒出来的决策 | **只追加**，不改写；改主意就新加一条，写明"取代第 N 条" |
| **已排除的方案** | 试过但行不通的方案和原因 | 只追加 |
| **拆解与进度** | 拆解方案、每一步的状态（未开始 / 进行中 / 已验证）、验证证据（命令 + 关键输出，晚于最后一次修改，见 [审查层](审查层.md)） | 进度可覆盖；**已验证的步骤不能悄悄改回未完成** |

三种写入方式对应书中持久状态的三种语义：检查点可以覆盖，事件历史只追加，已经确认的结果不能悄悄重来。

## 谁写、什么时候写

- **agent 写**，时机是每次停下来等你的时候，和给复位卡同时
- **你只确认"决策"部分**和你的表态一致，不用审整个文件

## 怎么用

- **丢掉会话重开**：新会话第一步读任务文件
- **并行**：每个任务一个文件，复位卡直接从文件读
- **放在哪**：放在仓库里，但**不提交**。它是过程状态，不是交付物。实现上放在每个 worktree 根目录的 `.agent-tasks/`，目录里放一个只写了 `*` 的 `.gitignore` 让它忽略自己：不改项目已提交的 `.gitignore`，也不写 `.git/`（写 `.git/` 属于受保护路径，每次都要人工批准）
- **多任务**：每个任务文件带 `status`（等表态 / 等审 / 执行中 / 卡住 / 已完成 / 已放弃），据此列出未完成的任务；任务属于它所在的 worktree，恢复时回到那个 worktree
- **决策清单一列出就整份写入**，每项标"待表态"，表态后在该项下追加。实践测试中发现：只在表态后才记录的话，会话在表态前丢掉，清单就跟着丢了

## 做完以后

- 值得长期保留的决策按 [上下文层](上下文层.md) 的准入测试处理：每个任务都需要的写进常驻规则文件；否则写进提交说明或架构决策记录
- 任务文件归档或删掉，不让它变成另一个需要维护的东西
