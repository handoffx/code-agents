# 决策清单格式

## 为什么是清单而不是计划

一个整体的计划，用户只能整体批准或否决，很容易看一眼觉得合理就批了。拆成一项项决策，每项都要用户明确表态，就很难走过场。

## 每一项的格式

写进任务文件、也作为提问内容的依据：

```
### D1. <要决定什么>
- 可选方案：A. … / B. …（至少两个）
- 我的倾向：A，因为 …
- 选错的代价：…；是否容易回退：…
- 依赖的系统事实：…（这项判断基于代码里的什么事实，指到文件或模块）
- 表态：待表态
```

## 怎么问：用 AskUserQuestion，一次一项

先把整份清单写进任务文件，在聊天里用几行概括有哪几项决策（只列标题），然后**用 AskUserQuestion 工具逐项提问，一次调用只问一个决策**。用户的反馈是：在选择框里一项一项选，比读完一大段文字再逐条打字回复轻松，也更不容易随手同意。

每次提问这样组织：

- **question**：写清要决定什么，并在问题里带上选错的代价和依据的事实。选择框打开时用户可能看不到前面的聊天内容，问题要能独立看懂
- **options**：每个可选方案一个选项。你的倾向放第一个，label 末尾加 "(Recommended)"；description 写这个方案意味着什么、代价是什么。选项上限 4 个：方案不足 4 个时，再加一个"交给你判断"
- 选择框自带"Other"可以自由输入。在 question 末尾提示一句：需要更多信息或想先听讲解，可以在 Other 里写"补充信息"或"先讲给我听"

拿到回答后，立刻在任务文件该项下追加一行"表态：…"，再问下一项。用户选了"补充信息"或"先讲给我听"时，先照做，再重新问这一项。

全部问完后，给复位卡，进入拆解。

没有 AskUserQuestion 工具时（例如非交互模式），退回文字清单：逐项列出，末尾附下面的回复说明，等用户逐条回复。

## 用户的五种回复

| 回复 | 含义 | 你接下来做什么 |
|---|---|---|
| 同意 | 采纳你的倾向。用户应能说出一句理由 | 记进任务文件 |
| 选另一个 | 用户选了别的方案 | 记进任务文件 |
| 交给你判断 | 用户不在意这一项 | 按你的倾向做，记为"交给 agent 判断"；同类决策以后不必再列 |
| 补充信息 | 选项和代价太抽象 | 落到具体代码：涉及哪些模块、以后哪里会变难改，然后请用户再表态 |
| 先讲给我听 | 用户不了解这一块 | 先讲清这一块现在是怎么工作的，然后请用户再表态 |

在选择框里，"同意"和"选另一个"就是选对应的方案，"交给你判断"是单独的选项（有空位时），"补充信息"和"先讲给我听"通过 Other 输入。

"补充信息"和"先讲给我听"不是负担。用户批了一项却说不清为什么，往往是信息不够或对这块不熟；这两个选项让问题在表态时就暴露，而不是等决策选错之后。
