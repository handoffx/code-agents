# task-contract:start

这个 skill 的核心想法：**拆解的单位是决策，不是代码行数；审查的是契约，不是 diff。** 用户的时间最贵，要花在定决策和判断上，而不是从聊天记录里回忆进度、或者从 diff 里倒推你的意图。所以你的工作方式是：先把用户在意的决策摆出来让用户定，再按定好的契约小步执行，每一步给出用户能核对的证据。

任务描述：$ARGUMENTS（为空时，任务就是用户刚才的请求）

## 开始前：检查当前 worktree 有没有进行中的任务

运行 `agent-tasks list`（插件自带的命令，已在 PATH 上）。如果**当前 worktree** 已有未完成的任务，先问用户：

- 接着做那个任务（转到 task-contract:resume）
- 在新的 worktree 里开始这个新任务（建议：`claude --worktree <名字>` 开一个新会话）。原因是两个任务同时改同一个工作区，会互相覆盖、互相干扰验证结果
- 确认两个任务不碰同一块代码后，在当前 worktree 继续

其他 worktree 里的任务不影响这里，不用问。

## ⓪ 值得做吗（只在任务由你提出时）

如果这个任务来自你之前的建议（调研结论、"顺便可以改进"的地方），先问用户值不值得做；值得的话，对价值不高的任务请用户顺便定一个预算（例如"最多一小时"）。用户自己提出的任务跳过这一步，提出时已经回答过了。

## ① 分级

判断标准只有一个：**有没有用户在意、但还没定下来的决策。** 不按代码量分。

| 级别 | 判断 | 走哪几步 |
|---|---|---|
| L0 | 没有未定决策 | 直接做，给出验证命令和结果 |
| L1 | 有，而且知道是哪几个 | 把这几个决策和你的倾向写在一句话里请用户确认，然后做 |
| L2 | 有，但列不全 | ③ 决策清单 → ④ 拆解 → ⑤ 执行 → ⑥ 报告 |
| L3 | 不知道会有哪些决策 | ② 探索 → ③ → ④ → ⑤ → ⑥ |

- 用一行说明你定的级别和理由，然后直接进入对应步骤，不用单独停下来等级别确认（L2 及以上第一次停下来就是决策清单，用户可以在那里纠正级别）
- **下限**：数据迁移、删除数据、对外接口与数据格式、鉴权与密钥、依赖升级，至少 L2。这些改动出了错发现慢、回退难
- 乐观起步，看到信号就升级：执行中冒出新决策、同一处被纠正两次、L0/L1 做到一大半卡住，都说明级别低了。从 L0/L1 升到 L2 时补建任务文件

L2 及以上在这里建任务文件：

```bash
agent-tasks new <简短英文名> --title "<任务标题>" --level L2
```

命令会打印文件路径。之后用编辑工具维护这个文件，规则见"任务文件"。

## ② 探索（L3）

目标是产出知识，不是代码：弄清现状、有哪些可行方案、各自会卡在哪里。可以写原型来获取证据（"方案 A 试过了，在 X 处会卡住"），但原型默认丢掉，探索的交付物是结论和决策清单。真正要保留的代码，在决策定下来之后按拆解重新写。试过不行的方案记进任务文件的"已排除的方案"。

## ③ 决策清单（L2 及以上）

先不要动手写实现。列出完成目标需要的决策，格式和回复方式见 `${CLAUDE_PLUGIN_ROOT}/references/decision-list.md`。要点：

- **只列选错了会影响用户的**。实现细节不列，但**实现方向要列**：数据结构、状态管理方式、模块划分，只要选错了以后很难改。原因：你倾向于选训练数据里最常见的做法，在通用场景下对，在这个项目里未必对，而这类方向选错是"接口没变、内部选错"最常见的来源
- 每项附上这项判断**依赖的系统事实**（如"X 模块同时被 Y 和 Z 调用"）。核对事实比做判断容易，事实错了用户当场就能发现
- 清单要短。项数多了，后面几项就会被随手同意
- 只覆盖任务内部的决策，"值不值得做"属于 ⓪

**先把整份清单写进任务文件的"决策"**，每项完整写出方案、倾向、代价和依据的事实，并标"待表态"。会话可能在用户表态之前就丢掉，清单只在聊天里的话，新会话只能重新分析一遍。然后停下（status 设为 `waiting-decision`），等用户逐项表态。用户回"补充信息"或"先讲给我听"时，照做后再请用户表态。表态在对应项下追加一行，不改原来的内容。

## ④ 拆解方案

用户表态后给出拆解方案。每一步都写明**怎么验证**；写不出验证方式，说明这一步还没准备好。

- **第一步写出整体验收的检查**（端到端的测试、脚本或明确的检查步骤），此时它应该失败；**最后一步让它通过**。每步验证都通过不等于整个任务完成，步骤之间的缝要靠它兜住
- 最后一步还要按项目的完成定义交付非代码产出（文档、迁移说明、changelog 等）。项目的完成定义通常写在 CLAUDE.md 里；没写就问用户
- 目标写成可观察的结果（"首页加载从 3 秒降到 1 秒以内"，而不是"优化性能"）
- 按验证方式区分步骤类型：
  - 探索型：验证是"用户能否据此做决策"
  - 保持行为型（重构、搬迁、铺路）：现有测试全过，**断言一行不改**；只允许机械性改动（改名、改导入路径），并单独列出来
  - 改变行为型（新功能、修 bug）：先有一个会失败的测试，再实现；测试由用户写或由用户审过
- 顺序：整体验收检查第一；其余不确定性高的先做；每一步结束时系统都能跑（纵向切片）；先定接口再写实现

写进任务文件的"拆解与进度"，然后停下（status 设为 `waiting-review`），等用户确认。

## ⑤ 小步执行

按拆解一步一步做（status 设为 `active`），每完成一步停下来交证据。

**证据必须可核对。** 贴出实际运行的命令和原始输出的关键几行（例如 `pytest tests/foo` → `12 passed`）。"测试已通过""我验证过了"这类只有结论的描述不算证据。**证据必须晚于这一步的最后一次修改**：先跑测试、又改了代码、再报告"通过"，验证的就是旧代码，这是实际发生过的问题。跑不了的验证（界面效果、需要真实环境的行为）给出截图或复现步骤；都做不到的不算已验证，记进已知缺口。

**新决策停下来问。** 执行中发现清单之外、选错了会影响用户的决策，停下来加进清单等用户表态（status 设为 `waiting-decision`），不要自己做掉。实现细节照常自行处理。这类停顿往往说明级别该升一级，顺便说明。

**同一处被纠正两次还不对，建议丢掉会话。** 反复纠正通常说明任务里藏着没暴露的决策或缺上下文，继续在这个会话里修只会越来越乱。此时把走不通的方案和原因记进"已排除的方案"，把暴露出来的决策补进清单，status 设为 `blocked`，建议用户开新会话用 task-contract:resume 接着做。

**做到一大半发现补不完时**，看剩下的部分里有什么：只是执行就补完；有没暴露的决策或方向错了，建议丢掉代码、保留任务文件、回到拆解；补完的代价超过任务价值（或超了预算），建议整个放弃（status 设为 `abandoned`）。已有代码重新生成很便宜，贵的是决策和教训，而它们都在任务文件里。

## 每次停下来：复位卡

只要停下来等用户（等表态、等审、卡住），先给一张复位卡。用户可能同时在多个 worktree 里跑多个任务，复位卡让用户不用回忆就能接上：

```
【复位卡】
目标：<一句话>
进度：第 N 步 / 共 M 步（或：决策清单待表态）
为什么停：等表态 | 等审 | 卡住
需要你做：<具体到一个动作>
相关决策：<一两条之前定过的>
```

L2 及以上同时更新任务文件：重写开头的复位卡，更新 frontmatter 的 `status` 和 `updated`。

## ⑥ 完成报告

全部步骤完成后，按以下结构报告。报告是用户审查的索引，帮用户知道该看哪里，所以要指到具体位置：

1. **决策逐项落实**：每个决策体现在 diff 的哪里（文件和位置）
2. **每步验证**：命令和关键输出
3. **整体验收**：是否通过，附命令和输出
4. **契约层面的变化**：新增或修改的接口、新抽象、新依赖、模块边界变化。用户要能对每一条说出判断理由，所以每条写清为什么这样做
5. **范围外的改动**：碰了计划外的文件、加了没要求的东西，逐条列出
6. **已知缺口**：没覆盖的情况、跑不了的验证；目标层面在会话里验证不了的，写明由谁、何时、看什么来确认

然后把 status 设为 `done`，提醒用户哪些决策值得长期保留（每个任务都需要的，建议写进 CLAUDE.md；否则写进提交说明），由用户决定是否删除任务文件。

## 任务文件（L2 及以上）

会话会丢，上下文会被压缩，决策不能跟着丢。结构说明见 `${CLAUDE_PLUGIN_ROOT}/references/task-file.md`。

- **位置**：`agent-tasks new` 建在当前 worktree 根目录的 `.agent-tasks/` 下，目录里有一个只写了 `*` 的 `.gitignore`，所以不会被提交，也不改动项目自己的文件
- **status**：`waiting-decision`（等表态）、`waiting-review`（等审）、`active`（执行中）、`blocked`（卡住）、`done`、`abandoned`。`agent-tasks list` 和会话开始时的提示都靠它判断哪些任务没完成，所以每次停下来都要更新
- **写入方式**：决策和已排除的方案**只追加**，改主意就新加一条并写明"取代 Dn"；进度可以覆盖，但已验证的步骤不能悄悄改回未完成；复位卡每次停下来时重写
